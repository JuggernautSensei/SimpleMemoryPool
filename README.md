# SimpleMemoryPool

메모리의 **할당·반납·재사용과 정렬**을 설명하기 위해 작성한 C++20 헤더 전용 구현입니다. 저수준 메모리 관리에 대한 이해를 점검하고, 메모리를 확보할 때부터 다음 할당 위치를 계산할 때까지 정렬을 직접 적용해 보는 목적으로 만들었습니다.

중심이 되는 구현은 같은 크기의 블록을 나누어 쓰는 `FixedBlockPool`입니다. 여기에 객체의 생성·소멸을 연결한 `ObjectPool`, 메모리를 순차적으로 할당하고 한 번에 해제하는 `MemoryArena`를 함께 담았습니다.

이 README에서는 핵심 동작과 사용 방법을 설명합니다. 멤버 변수부터 할당·반납 코드를 따라가는 상세 해설은 블로그 포스팅 [메모리 풀에 대한 기본적인 개념과 구현](https://juggernautsensei.notion.site/3c5c3fb6c02f8041b2d5e177d24cab3d?source=copy_link)에 정리했습니다.

## 큰 메모리를 블록으로 나누어 씁니다

`malloc/free` 같은 범용 할당자는 크기와 수명이 서로 다른 요청을 처리합니다. 같은 크기의 메모리를 반복해서 사용하는 경우에는 문제의 범위를 좁힐 수 있습니다. 큰 메모리 영역 하나를 확보하고 일정한 크기의 블록으로 나누면, 개별 할당 요청마다 범용 할당자를 호출하지 않아도 됩니다.

[`FixedBlockPool`](FixedBlockPool.h)은 블록 크기, 풀 하나에 들어갈 블록 수, 정렬 단위를 생성자에서 받습니다. 실제 메모리는 첫 `Alloc()`에서 확보하고, 반납된 블록도 없고 현재 풀의 블록도 모두 사용했다면 새 풀을 추가합니다.

```text
풀 하나의 배치
[풀 헤더][정렬 패딩][블록 0][블록 1][블록 2] ... [블록 N-1]
                       ^
                     m_pCur → 다음에 내어줄 블록

새 풀의 헤더 → 이전 풀의 헤더 → ... → nullptr
```

아직 사용하지 않은 블록을 내어줄 때는 커서 `m_pCur`이 가리키는 주소를 반환하고, 커서를 정렬된 블록 크기만큼 전진시킵니다. 어느 크기의 빈 공간을 고를지 탐색할 필요가 없는 대신, 모든 요청이 같은 블록 크기를 사용합니다. 블록보다 작은 데이터를 담으면 남는 공간은 그 할당에서 사용하지 않습니다.

풀의 앞부분에는 이전 풀을 가리키는 포인터를 둡니다. 덕분에 확보한 풀들을 별도 컨테이너 없이 연결해 두었다가 `Reset()`이나 소멸 시 순회하며 해제할 수 있습니다.

## 반납한 블록 안에 재사용 정보를 기록합니다

`Free()`의 반납은 범용 할당자에 메모리를 돌려준다는 뜻이 아닙니다. 사용이 끝난 블록을 **다시 할당할 수 있는 상태로 바꾼다**는 뜻입니다. 실제 메모리는 풀이 계속 보유합니다.

반납된 블록은 더 이상 사용자 데이터를 유지할 필요가 없습니다. 그래서 그 공간의 앞부분에 다음 빈 블록의 주소를 기록하고, 빈 블록 목록인 **free list**로 연결합니다. 데이터 자체에 연결 정보를 넣는 intrusive linked list 방식이므로 목록의 노드를 위한 추가 할당이 필요하지 않습니다.

```text
블록 A 반납: free list → A → nullptr
블록 B 반납: free list → B → A → nullptr
다음 할당:  B를 반환하고, free list → A → nullptr
```

`Alloc()`은 새 블록을 내어주기 전에 이 목록을 먼저 확인합니다. 빈 블록이 있으면 목록의 맨 앞에서 하나를 꺼내 반환합니다. 반납할 때도 맨 앞에 붙이기 때문에 가장 최근에 반납한 블록부터 재사용합니다.

풀 추가가 필요 없는 할당과 개별 반납은 일정한 수의 포인터 연산으로 처리됩니다. 다만 새 풀을 추가할 때는 기반 할당자를 호출하고, `Reset()`은 확보한 풀 전체를 순회합니다. 모든 경로의 비용이 같은 것은 아닙니다.

## 다음 블록의 주소도 정렬되어야 합니다

메모리 정렬은 주소가 특정 수의 배수가 되어야 한다는 조건입니다. 예를 들어 16바이트 정렬을 요구하는 데이터는 시작 주소가 16의 배수여야 합니다. 처음 확보한 메모리의 주소만 맞추는 것으로는 충분하지 않습니다. 헤더를 건너뛴 첫 블록과, 그 뒤에 차례로 내어줄 블록들도 정렬 조건을 유지해야 합니다.

이 구현은 세 곳에서 정렬을 적용합니다.

1. 기반 할당자에서 요청한 정렬에 맞는 풀 메모리를 확보합니다.
2. 풀 헤더 크기를 정렬 단위로 올림해 첫 블록의 위치를 정합니다.
3. 블록 크기도 같은 단위로 올림해 커서를 전진시킵니다.

예를 들어 포인터가 8바이트인 환경에서 블록당 24바이트와 16바이트 정렬을 요청하면, 헤더 영역은 패딩을 포함해 16바이트가 되고 블록 간 간격은 32바이트가 됩니다.

```text
16바이트로 정렬된 풀 시작 주소를 기준으로 한 오프셋

0          8         16                    48                    80
[헤더 8B  ][패딩 8B  ][블록 0: 24B + 패딩 8B][블록 1: 24B + 패딩 8B]
                      ^                     ^
                   첫 블록                다음 블록
```

처음 블록이 정렬되어 있고 이후 주소도 32바이트씩 증가하므로, 모든 블록의 시작 주소가 16바이트 정렬을 유지합니다. 이를 위해 [`Base.h`](Base.h)의 `AlignUp()`에서 사용하는 계산은 다음과 같습니다.

```cpp
(size + (alignment - 1)) & ~(alignment - 1)
```

`alignment`가 2의 거듭제곱이라는 전제에서, 크기나 주소를 해당 정렬 단위의 배수로 올림하는 계산입니다. [`FixedBlockPool.h`](FixedBlockPool.h)에서는 이 계산으로 헤더 크기와 블록 크기를 맞춥니다. 전체 풀의 크기는 다음과 같습니다.

```text
정렬된 헤더 크기 + 정렬된 블록 크기 × 풀당 블록 수
```

블록의 크기·정렬은 반납 이후에도 중요합니다. 빈 블록에는 다음 블록의 포인터를 기록하므로, 그 포인터가 들어갈 크기와 정렬 조건까지 만족해야 합니다.

## 객체 풀과 아레나는 수명을 다르게 다룹니다

[`ObjectPool<T>`](ObjectPool.h)는 `FixedBlockPool`에 객체의 생성과 소멸을 연결합니다. `New()`는 메모리를 받은 뒤 `std::construct_at()`으로 전달받은 인자를 사용해 객체를 생성하고, `Delete()`는 `std::destroy_at()`으로 소멸자를 호출한 뒤 블록을 반납합니다. 메모리 확보와 객체 생성은 서로 다른 단계입니다.

객체 풀은 살아 있는 객체 목록을 추적하지 않습니다. 따라서 풀을 소멸시키는 것만으로 남은 객체의 소멸자가 호출되지는 않습니다. 생성한 객체는 풀보다 먼저 `Delete()`해야 합니다.

[`MemoryArena`](MemoryArena.h)는 개별 반납이 필요 없는 경우를 다룹니다. 요청마다 커서를 정렬하고 필요한 크기만큼 전진시키며, 현재 풀에 공간이 없으면 새 풀을 추가합니다. 개별 `Free()`는 없고 `Reset()`이나 소멸 시 확보한 메모리를 한꺼번에 해제합니다. 한 작업 동안 필요한 임시 데이터를 모아 두고 작업이 끝날 때 모두 버리는 흐름에 맞는 구조입니다.

아레나 구현은 *Physically Based Rendering(PBRT)*에서 본 구조를 참고해 만들었습니다. 이 구현의 `Reset()`은 커서만 되돌리는 것이 아니라 확보한 풀들을 실제로 해제합니다. 또한 원시 메모리만 제공하므로, 그 안에 객체를 직접 생성했다면 필요한 소멸자 호출도 사용자가 관리해야 합니다.

## 사용 방법

외부 라이브러리나 별도 링크 과정 없이 저장소 루트를 헤더 탐색 경로에 추가하면 됩니다. 전체 헤더를 사용하려면 `std::construct_at()`을 제공하는 **C++20 이상**이 필요합니다.

| 헤더 | 역할 |
| --- | --- |
| [`Base.h`](Base.h) | 크기·주소 정렬 계산, 플랫폼별 정렬 메모리 할당·해제 |
| [`FixedBlockPool.h`](FixedBlockPool.h) | 같은 크기의 블록 할당·반납·재사용 |
| [`ObjectPool.h`](ObjectPool.h) | 타입별 객체 생성·소멸과 블록 재사용 연결 |
| [`MemoryArena.h`](MemoryArena.h) | 요청 크기별 순차 할당과 일괄 해제 |

메모리 확보에는 MSVC 환경에서 `_aligned_malloc/_aligned_free`, 그 외 환경에서 `posix_memalign/free`를 사용합니다. 따라서 MSVC 또는 `posix_memalign()`을 지원하는 POSIX 환경을 대상으로 합니다.

### 고정 크기 블록을 반납하고 재사용하기

아래 예제는 32바이트 블록을 할당해 사용하고 반납합니다. 다음 요청에서 같은 블록을 재사용하는 것도 확인할 수 있습니다.

```cpp
#include <cassert>
#include <cstring>
#include "FixedBlockPool.h"

int main()
{
    jug::FixedBlockPool pool(32, 127);

    void* first = pool.Alloc();
    std::memset(first, 0, 32);
    pool.Free(first);

    void* reused = pool.Alloc();
    assert(reused == first);
    pool.Free(reused);
}
```

### 객체를 생성하고 소멸시키기

현재 `ObjectPool<T>`는 `sizeof(T)`와 `alignof(T)`를 그대로 기반 풀에 전달합니다. 예제에서는 반납 시 포인터를 기록할 수 있도록 `alignas(void*)`를 지정했습니다. 크기나 정렬이 작은 타입을 자동으로 포인터 기준에 맞춰 주지는 않습니다. 예를 들어 `alignof(int) < alignof(void*)`인 환경에서는 `ObjectPool<int>`를 사용할 수 없습니다.

```cpp
#include <cassert>
#include "ObjectPool.h"

struct alignas(void*) Particle
{
    float x;
    float y;

    Particle(float _x, float _y) : x(_x), y(_y) {}
};

int main()
{
    jug::ObjectPool<Particle> particles(128);

    Particle* particle = particles.New(1.0f, 2.0f);
    assert(particle->x == 1.0f && particle->y == 2.0f);
    particles.Delete(particle);
}
```

### 임시 메모리를 한꺼번에 해제하기

`MemoryArena`의 생성자 인자는 개별 할당 크기가 아니라 내부 풀 하나의 크기입니다. 아래에서는 4,096바이트 풀 안에서 32바이트 정렬을 만족하는 64바이트 공간을 할당합니다.

```cpp
#include <cstring>
#include "MemoryArena.h"

int main()
{
    jug::MemoryArena arena(4096);

    void* buffer = arena.AlignedAlloc(64, 32);
    std::memset(buffer, 0, 64);

    arena.Reset();
    // buffer는 더 이상 사용할 수 없습니다.
}
```

## 포스팅의 성능 비교

아래는 [포스팅](https://juggernautsensei.notion.site/3c5c3fb6c02f8041b2d5e177d24cab3d?source=copy_link)에 기록한 `malloc/free`와 `FixedBlockPool`의 기존 측정 결과입니다. 새로운 환경에서 다시 측정한 결과는 아닙니다.

기록된 조건은 MSVC, x64 Release, 32바이트 블록, 풀당 127블록입니다. 풀 하나의 크기는 헤더·패딩 16바이트를 포함해 4,080바이트로 기록되어 있습니다. 이는 위의 크기 계산에서 헤더 영역이 16바이트일 때의 값이며, 기본 정렬값이 다른 환경에서도 같은 크기가 된다는 뜻은 아닙니다.

| 시나리오 | malloc/free | FixedBlockPool | 시간 비율¹ |
| --- | ---: | ---: | ---: |
| 200만 회 할당 후 일괄 해제 | 144.851 ms | 18.704 ms | 7.74배 |
| 할당 직후 해제 500만 회 반복 | 157.437 ms | 2.950 ms | 53.38배 |
| 랜덤 할당·해제 혼합, 동시 생존 1만 개 | 145.569 ms | 47.004 ms | 3.10배 |
| 사전 힙 파편화 + 프레임 단위 생성·즉시 소멸 | 136.961 ms | 6.558 ms | 20.88배 |

¹ `malloc/free`의 측정 시간을 `FixedBlockPool`의 측정 시간으로 나눈 값입니다.

이 기록에서 가장 큰 차이가 난 경우는 할당 직후 반납을 반복하는 시나리오입니다. 구현을 보면 이 패턴에서는 같은 free list의 맨 앞 블록을 꺼냈다 붙이는 동작을 반복하게 됩니다. 반면 할당·반납 순서가 뒤섞인 시나리오에서는 시간 비율이 3.10배로 줄어듭니다. 단일 수치보다 할당 패턴에 따른 차이를 함께 볼 필요가 있습니다.

벤치마크 소스는 현재 저장소에 없고, 포스팅에도 CPU·컴파일러 버전이나 반복 측정 통계까지 기록되어 있지는 않습니다. 따라서 위 수치를 다른 환경이나 일반적인 메모리 할당 성능으로 확대해 해석하기는 어렵습니다. 세부 시나리오와 당시 결과는 포스팅에서 확인할 수 있습니다.

## 호출자가 지켜야 할 조건

메모리 풀의 동작을 설명하기 위한 최소 구현으로, 올바른 크기·정렬·수명의 관리는 호출자의 책임입니다. 모든 잘못된 사용을 검사하는 구현은 아닙니다.

- **블록 크기와 정렬:** 정렬 후 블록 크기는 `sizeof(void*)` 이상, 블록 정렬은 `alignof(void*)` 이상이어야 합니다. 정렬은 2의 거듭제곱이어야 하고, 풀당 블록 수는 0보다 커야 합니다. 크기 계산에서 정수 오버플로가 발생하지 않는 값이어야 합니다.
- **블록 반납:** 해당 풀에서 할당받아 아직 반납하지 않은 블록만 반납해야 합니다. 다른 풀의 포인터와 중복 반납을 검사하지 않습니다. 반납 이후에는 그 블록의 데이터를 사용할 수 없습니다.
- **객체 수명:** `FixedBlockPool`은 생성자·소멸자를 호출하지 않습니다. `ObjectPool`에서 만든 객체는 풀 소멸 전에 `Delete()`해야 합니다. `New()` 중 생성자 예외가 발생했을 때 할당 블록을 되돌리는 처리도 제공하지 않습니다.
- **아레나 요청 크기:** 요청 크기와 헤더·최대 정렬 패딩이 내부 풀 하나에 들어가야 합니다. 단일 요청에 맞춰 풀 크기를 늘리는 기능은 없습니다. 코드의 조건은 `sizeof(LINK) + alignment - 1 + size <= 내부 풀 크기`이며, `LINK`는 내부 풀 헤더입니다.
- **동시 접근:** 내부 동기화가 없으므로 같은 인스턴스에 대한 동시 접근은 외부에서 동기화해야 합니다.
- **할당 실패:** 기반 할당자가 실패했을 때 이를 호출자에게 안전하게 반환하거나 복구하는 처리가 없습니다. `Alloc()`의 실패가 `nullptr`로 보고된다고 가정할 수 없습니다.

일부 전제조건은 `JUG_ASSERT`로 검사합니다. 기본 정의는 표준 `assert`이므로 `NDEBUG`가 정의된 빌드에서는 검사가 비활성화됩니다. `Base.h`를 포함하기 전에 `JUG_ASSERT(cond, msg)`를 정의하면 사용 중인 assertion으로 교체할 수 있습니다.

`FixedBlockPool`과 `MemoryArena`의 메모리에 객체를 직접 생성했다면, 필요한 소멸자는 `Reset()` 또는 풀 소멸 전에 호출해야 합니다. 전체 메모리 해제 이후에는 해당 메모리에서 받은 모든 포인터가 무효입니다.
